Interactive series guide

Build a local LLM workflow one layer at a time.

This guided path turns the local LLM series into a practical map: hardware reality, toolchain, model choice, identity, hosted fallback, coding agents, reusable instructions, MCP, and the final stack.

A local model is not abstract. It has to fit into RAM, VRAM, disk, heat, runtime support, and patience.

01

Start with the computer, not the leaderboard.

The first local LLM decision is not which model sounds most impressive. It is what can run well enough on your actual machine. RAM, VRAM, context length, quantization, and runtime support decide whether the experience feels useful or painful.

Local gives you privacy control and offline use. It also gives you the job of managing memory, speed, files, and heat.

02

Turn the tool pile into a pipeline.

uv keeps Python environments and dependencies sane. uvx runs disposable Python CLIs. Ollama downloads, stores, and serves local models. A client, notebook, script, editor, or agent sends prompts.

Once those jobs are separated, the setup feels much less mysterious.

03

Choose with evidence.

Llama, Qwen, Gemma, Mistral, DeepSeek, Phi, gpt-oss, and coder models are families, not answers. Write a tiny evaluation set with tasks you actually care about, then compare quality, speed, memory, and failure modes.

04

Track the exact thing you ran.

A model family name is not enough. The exact checkpoint, quantization, runtime, prompt template, context setting, and provider path can change the result. Good notes make local experiments repeatable.

05

Add reach only when the task justifies it.

OpenRouter can make many hosted models feel like one API. That is useful for comparison, fallback, and larger contexts. But requests leave the local boundary, and provider routing affects privacy, cost, moderation, and feature support.

The practical pattern is local-first, hosted when the benefit is worth the boundary change.

06

Chat is not the same thing as an agent.

Local LLMs are useful for private drafts. Coding agents become useful when the task needs repository context, controlled tool access, command output, browser checks, and iterative repair.

07

Stop retyping the same instruction.

Once you repeat a workflow, turn it into a rule, skill, agent, or subagent. That might be a blog editor, a local model evaluator, a PR reviewer, or a literature-search workflow.

With local LLMs, the surrounding app has to load these instructions and connect the tools.

08

The model does not magically know your files.

MCP is a protocol for connecting AI clients to tools and context. The model itself still predicts text. The client decides what to expose, what to call, and what permission boundary to enforce.

09

Build the system you can explain.

Start with one local runtime and one model. Add a fixed evaluation set. Add a client. Add tools and reusable instructions. Add hosted fallback only when local quality or context is not enough.

Choose your path

Different goals need different boundaries.

Privacy-firstStay local, keep tools read-only, avoid hosted fallback for sensitive prompts. Low-cost learnerUse small instruct models, fixed prompts, and occasional hosted comparison. Coding-heavyUse local drafts, then a coding agent when edits and tests matter. Hybrid stackStart local and escalate selected context when the task needs more.
