A Knowledge Graph for Local LLMs

June 6, 2026

  • Local LLMs
  • Knowledge Graph
  • AI Models
  • MCP
  • AI Tools

Local LLMs are easier to understand when the pieces are shown as a system instead of a list. A model does not exist alone. It sits inside a stack of hardware, runtimes, file formats, prompts, tools, permissions, and sometimes hosted fallback.

This post turns the local LLM series into an HTML-based knowledge graph. Click a node to see what it depends on. Use the filters to focus on one part of the system.

How to read the graph

Start on the left with hardware and model choice. These concepts answer the practical question: what can I run, and what should I test? Move through the runtime layer to see how a model becomes usable through Ollama, a local API, or a client application.

The upper-right side explains why model identity is slippery. The same family name can hide different checkpoints, file formats, quantization levels, prompt templates, and provider settings.

The lower-right side shows how local LLMs become more useful. MCP connects tools and context. Skills and rules make repeated workflows durable. Coding agents combine model reasoning with workspace access, tool use, and verification.

The main lesson

A local LLM is not one thing. It is a stack:

  1. Hardware decides what is practical.
  2. Runtime decides what can be loaded and served.
  3. Model choice depends on task, hardware, and constraints.
  4. Prompt harness and quantization change behavior.
  5. Clients, MCP, skills, and agents turn a model into a workflow.
  6. Hosted routers such as OpenRouter can be useful fallback, but they change the privacy and provider boundary.

Use the graph as a debugging map. When something feels confusing, ask which node changed.
