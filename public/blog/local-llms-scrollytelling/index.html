01

Start with the machine, not the leaderboard.

The first local LLM decision is not which model sounds most impressive. It is what can run well enough on your actual computer. RAM, VRAM, context length, quantization, and runtime support decide whether the experience feels useful or painful.

Local gives you privacy control and offline use. It also gives you the job of managing memory, speed, files, and heat.

02

Separate project tools from model runtimes.

uv keeps Python environments and dependencies sane. uvx runs disposable Python CLIs. Ollama downloads, stores, and serves local models. A client, notebook, script, editor, or agent sends prompts.

Once those jobs are separate, the stack becomes much easier to debug.

03

Do not collect model names. Test model fit.

Llama, Qwen, Gemma, Mistral, DeepSeek, Phi, gpt-oss, and coder variants all point to different strengths. A useful model is the one that passes your real writing, coding, summarization, structured-output, or research tasks.

A five-prompt evaluation set is more useful than ten vibes-based recommendations.

04

Same name does not mean same system.

qwen3:8b in Ollama, a Hugging Face checkpoint, and an OpenRouter endpoint can behave differently. The model family may be the same, while the checkpoint, quantization, runtime, provider, and prompt harness differ.

When behavior changes, inspect the stack before blaming the model.

05

Use hosted routers as an escape hatch, not a blur.

OpenRouter can make many hosted models feel like one API. That is useful for comparison, fallback, and larger contexts. But requests leave the local boundary, and provider routing affects privacy, cost, moderation, and feature support.

The practical pattern is local-first, hosted when the task justifies it.

06

A coding agent does not just answer. It works inside the project.

Claude Code, Codex, and Antigravity show the difference between chat and agentic development: reading files, editing code, running commands, inspecting failures, and revising from evidence.

Local LLMs are useful for private drafts. Coding agents become useful when the task needs action and verification.

07

Stop retyping the same instructions.

Rules, skills, agents, and subagents turn repeated guidance into reusable behavior. A rule says what should always be true. A skill packages a workflow. A subagent gives one focused job to a separate helper.

With local LLMs, the surrounding app has to load these instructions and connect the tools.

08

MCP is plumbing, not magic.

MCP standardizes how an AI app can provide tools and context. A server might expose files, GitHub issues, notes, databases, search, or a custom evaluation harness.

Resources provide context. Tools perform actions. Permissions decide the blast radius.

09

The win is not one magic model. It is a stack you understand.

Start with one local runtime and one model. Add a fixed evaluation set. Add a client. Add tools and reusable instructions. Add hosted fallback only when local quality or context is not enough.

That stack is small enough to debug and flexible enough to grow.

Choose your path

Use the scrolly as the map. Use the chapters as the field guide.

Privacy-firstStay local, keep tools read-only, avoid hosted fallback for sensitive prompts. Low-cost learnerUse small instruct models, fixed prompts, and occasional hosted comparison. Coding-heavyUse local drafts, then a coding agent when edits and tests matter. Hybrid stackStart local and escalate selected context when the task needs more.
