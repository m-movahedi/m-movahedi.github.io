In LLM 102, we introduced Retrieval-Augmented Generation (RAG) as a way to connect a language model to external knowledge. This post goes one layer deeper. We will look at how a RAG system actually works: embeddings, chunking, vector search, reranking, prompt assembly, citations, and evaluation.

The basic idea is simple: when the model needs knowledge, do not ask it to rely only on its parameters. Retrieve relevant evidence, place that evidence into the context window, and ask the model to answer from that evidence.

## 1. Why RAG Exists

LLMs store some knowledge in their parameters, but that knowledge can be incomplete, stale, private, or difficult to inspect. RAG adds a second memory: an external collection of documents that can be searched at inference time.

This distinction matters:

<div class="llm103-two-col">
  <div class="llm103-panel">
    <strong>Parametric memory</strong>
    <p>Knowledge stored in model weights.</p>
    <p>Fast to use, but hard to update directly.</p>
    <p>Can be wrong or outdated.</p>
  </div>
  <div class="llm103-panel">
    <strong>Retrieved memory</strong>
    <p>Knowledge stored in documents, databases, or files.</p>
    <p>Easier to update, inspect, cite, and restrict.</p>
    <p>Only useful if retrieval finds the right evidence.</p>
  </div>
</div>

For research, RAG is useful when the model needs to answer from papers, reports, datasets, lab notes, interview transcripts, policy documents, or project-specific files. Instead of asking, "What do you know about this?", we ask, "Given these retrieved sources, what answer is supported?"

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2005.11401">Lewis et al. (2020), "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"</a>: the core RAG paper connecting generation with retrieved external knowledge.</li>
    <li><a href="https://arxiv.org/abs/2002.08909">Guu et al. (2020), "REALM"</a>: an important retrieval-augmented pretraining approach for open-domain question answering.</li>
  </ul>
</div>

## 2. The RAG Pipeline

A RAG system has two sides: indexing and answering.

Indexing happens before the user asks a question. Documents are loaded, split into chunks, embedded, and stored. Answering happens at query time. The user question is embedded, similar chunks are retrieved, the best evidence is selected, and the LLM writes an answer.

<div class="llm103-flow" role="img" aria-label="RAG pipeline from documents to answer">
  <div class="llm103-card">
    <strong>Load</strong>
    <p>Collect documents and metadata.</p>
  </div>
  <div class="llm103-card">
    <strong>Chunk</strong>
    <p>Split into useful passages.</p>
  </div>
  <div class="llm103-card">
    <strong>Embed</strong>
    <p>Convert chunks into vectors.</p>
  </div>
  <div class="llm103-card">
    <strong>Retrieve</strong>
    <p>Find likely evidence.</p>
  </div>
  <div class="llm103-card">
    <strong>Rerank</strong>
    <p>Choose the strongest passages.</p>
  </div>
  <div class="llm103-card">
    <strong>Answer</strong>
    <p>Generate with citations.</p>
  </div>
</div>

The design choices in the middle matter more than people expect. A weak chunking strategy can bury evidence. A weak retriever can miss it. A weak prompt can cause the model to ignore it. RAG is a system problem, not just a vector database problem.

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2312.10997">Gao et al. (2023), "Retrieval-Augmented Generation for Large Language Models: A Survey"</a>: maps the RAG design space from naive pipelines to advanced and modular systems.</li>
    <li><a href="https://arxiv.org/abs/2307.03172">Liu et al. (2023), "Lost in the Middle"</a>: explains why retrieved evidence placement inside the context window can affect whether the model uses it.</li>
  </ul>
</div>

## 3. Embeddings: Turning Text into Searchable Vectors

An embedding model converts text into a vector. Similar meanings should land near each other in vector space. This lets us search semantically, not just by exact keyword overlap.

For example, a question like:

<div class="llm103-code">How do residents decide whether to evacuate before a hurricane?</div>

might retrieve chunks containing terms like:

<div class="llm103-pill-row" aria-label="Semantically related retrieval terms">
  <span class="llm103-pill">risk perception</span>
  <span class="llm103-pill">protective action decision</span>
  <span class="llm103-pill">warning response</span>
  <span class="llm103-pill">household evacuation</span>
  <span class="llm103-pill">social cues</span>
</div>

This is the strength of dense retrieval: it can connect related concepts even when the words differ. The weakness is that semantic similarity is not the same as factual usefulness. A passage can be topically similar but still not answer the question.

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/1908.10084">Reimers and Gurevych (2019), "Sentence-BERT"</a>: a foundational sentence embedding paper for efficient semantic similarity.</li>
    <li><a href="https://arxiv.org/abs/2004.04906">Karpukhin et al. (2020), "Dense Passage Retrieval"</a>: a major dense retrieval paper for open-domain question answering.</li>
    <li><a href="https://arxiv.org/abs/2112.09118">Izacard et al. (2021), "Contriever"</a>: important for unsupervised dense retrieval using contrastive learning.</li>
  </ul>
</div>

## 4. Chunking: The Quiet Part That Breaks Everything

Chunking is the process of splitting documents into pieces. It sounds mundane, but it is one of the most important RAG decisions.

Chunks that are too small may lose context. Chunks that are too large may bury the answer and waste the context window. Chunks that ignore document structure may separate a table from its explanation, a figure from its caption, or a claim from its citation.

<div class="llm103-grid">
  <div class="llm103-card">
    <strong>Small chunks</strong>
    <p>Precise retrieval, but context may be missing.</p>
    <div class="llm103-score"><span style="width: 38%;"></span></div>
  </div>
  <div class="llm103-card">
    <strong>Medium chunks</strong>
    <p>Often a practical starting point.</p>
    <div class="llm103-score"><span style="width: 72%;"></span></div>
  </div>
  <div class="llm103-card">
    <strong>Large chunks</strong>
    <p>More context, but more noise.</p>
    <div class="llm103-score"><span style="width: 54%;"></span></div>
  </div>
</div>

There is no universal best chunk size. A legal document, a research paper, a spreadsheet, and a meeting transcript need different handling. Good chunking preserves meaning, source location, and metadata.

Useful metadata often includes:

- document title;
- author or source;
- date;
- section heading;
- page number;
- file path;
- table or figure identifier;
- access permissions.

<div class="llm103-note">
  <p><strong>Practical starting point:</strong> chunk by document structure first, then use token length as a constraint. Headings, paragraphs, tables, and captions usually know more about meaning than a fixed character count does.</p>
</div>

## 5. Retrieval: Sparse, Dense, and Hybrid Search

RAG systems often combine several retrieval methods.

**Sparse retrieval** uses exact or near-exact term matching. BM25 is the classic example. It works well when the query uses distinctive terms, names, citations, acronyms, or technical phrases.

**Dense retrieval** uses embedding similarity. It works well when the query and document use different words for similar ideas.

**Hybrid retrieval** combines both. In practice, hybrid search is often a strong default because keyword matching and semantic matching fail in different ways.

<div class="llm103-two-col">
  <div class="llm103-panel">
    <strong>Keyword strength</strong>
    <p>Finds exact terms like "NHERI", "AASHTO", "TPB", or "Table 3".</p>
  </div>
  <div class="llm103-panel">
    <strong>Embedding strength</strong>
    <p>Finds related meaning like "evacuation intention" and "willingness to leave".</p>
  </div>
</div>

After retrieval, many systems use approximate nearest-neighbor indexes to make vector search fast at scale. That is where algorithms and libraries such as HNSW and FAISS enter the picture.

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2004.04906">Karpukhin et al. (2020), "Dense Passage Retrieval"</a>: a key reference for dense retrieval in open-domain QA.</li>
    <li><a href="https://arxiv.org/abs/1603.09320">Malkov and Yashunin (2016), "Efficient and Robust Approximate Nearest Neighbor Search Using HNSW"</a>: foundational for HNSW-style approximate vector search.</li>
    <li><a href="https://arxiv.org/abs/1702.08734">Johnson, Douze, and Jegou (2017), "Billion-Scale Similarity Search with GPUs"</a>: the FAISS paper, important for large-scale vector search systems.</li>
  </ul>
</div>

## 6. Reranking: Retrieval Is Not the Final Answer

Initial retrieval is usually broad. It tries to avoid missing relevant evidence. Reranking is more careful. It takes the candidate passages and scores which ones are actually useful for the specific question.

The difference is subtle but important:

<div class="llm103-grid">
  <div class="llm103-card">
    <strong>Candidate A</strong>
    <p>Topically similar but too general.</p>
    <div class="llm103-score"><span style="width: 45%;"></span></div>
  </div>
  <div class="llm103-card">
    <strong>Candidate B</strong>
    <p>Directly answers the question.</p>
    <div class="llm103-score"><span style="width: 91%;"></span></div>
  </div>
  <div class="llm103-card">
    <strong>Candidate C</strong>
    <p>Shares words but wrong context.</p>
    <div class="llm103-score"><span style="width: 24%;"></span></div>
  </div>
</div>

Reranking can be done with cross-encoders, late-interaction models, LLM judges, or task-specific scoring rules. The tradeoff is speed versus quality. A reranker is slower than first-stage retrieval, but it can sharply improve what enters the prompt.

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2004.12832">Khattab and Zaharia (2020), "ColBERT"</a>: introduced late interaction as an effective middle ground between efficient retrieval and expressive matching.</li>
    <li><a href="https://arxiv.org/abs/1908.10084">Reimers and Gurevych (2019), "Sentence-BERT"</a>: useful for understanding the bi-encoder versus cross-encoder tradeoff in semantic matching.</li>
  </ul>
</div>

## 7. Prompt Assembly and Citations

After retrieval and reranking, the system must assemble the prompt. This is where many RAG systems quietly succeed or fail.

A practical prompt should separate the user's question from the retrieved evidence and make the model's obligations clear:

<div class="llm103-code">Use only the evidence below.
If the evidence is insufficient, say what is missing.
Cite sources using [source_id].

Question:
What factors influenced evacuation intention?

Evidence:
[S1] ...
[S2] ...
[S3] ...</div>

Citations should point to the retrieved source, not just decorate the answer. A useful citation lets the reader inspect the document, page, section, or chunk that supports the claim.

Good RAG answers tend to:

- answer the question directly;
- cite each factual claim;
- distinguish evidence from inference;
- avoid using retrieved text that is irrelevant;
- say when the sources do not support an answer.

<div class="llm103-note">
  <p><strong>Important habit:</strong> make unsupported answers visibly worse than cautious answers. If the system rewards polished confidence, it will produce polished confidence.</p>
</div>

## 8. Evaluation: Measuring the Whole System

RAG evaluation is not one number. You need to evaluate retrieval and generation separately, then evaluate the complete workflow.

For retrieval, ask:

- Did the system retrieve a source that contains the answer?
- Was the source ranked high enough to fit into the context window?
- Did retrieval work for paraphrased queries?
- Did it handle acronyms, dates, tables, and domain terms?

For generation, ask:

- Is the answer faithful to the retrieved evidence?
- Are citations attached to the right claims?
- Does the model admit when evidence is missing?
- Is the answer useful for the intended audience?

<div class="llm103-grid">
  <div class="llm103-card">
    <strong>Retrieval recall</strong>
    <p>Can the system find the right evidence?</p>
  </div>
  <div class="llm103-card">
    <strong>Faithfulness</strong>
    <p>Does the answer stay grounded in evidence?</p>
  </div>
  <div class="llm103-card">
    <strong>Usefulness</strong>
    <p>Does the final response solve the user's task?</p>
  </div>
</div>

A small hand-built evaluation set is often more valuable than a big vague one. For a research website or lab assistant, you might create 30-50 representative questions with known supporting sources and expected answer traits.

<div class="llm103-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2303.08896">Manakul, Liusie, and Gales (2023), "SelfCheckGPT"</a>: useful for thinking about consistency-based hallucination detection.</li>
    <li><a href="https://arxiv.org/abs/2109.07958">Lin, Hilton, and Evans (2021), "TruthfulQA"</a>: a benchmark for truthfulness and imitative falsehoods in language models.</li>
    <li><a href="https://arxiv.org/abs/2312.10997">Gao et al. (2023), "Retrieval-Augmented Generation for Large Language Models: A Survey"</a>: includes discussion of RAG evaluation challenges and system variants.</li>
  </ul>
</div>

## 9. Common Failure Modes

RAG reduces some LLM risks, but it creates its own stack of failure modes.

<div class="llm103-grid">
  <div class="llm103-card">
    <strong>Bad chunks</strong>
    <p>The answer is split away from needed context.</p>
  </div>
  <div class="llm103-card">
    <strong>Missed retrieval</strong>
    <p>The right source never reaches the model.</p>
  </div>
  <div class="llm103-card">
    <strong>Context overload</strong>
    <p>Too much retrieved text dilutes the important passage.</p>
  </div>
  <div class="llm103-card">
    <strong>Wrong citation</strong>
    <p>The answer is plausible but points to the wrong source.</p>
  </div>
  <div class="llm103-card">
    <strong>Stale index</strong>
    <p>The document store is not synchronized with reality.</p>
  </div>
  <div class="llm103-card">
    <strong>Permission leak</strong>
    <p>The retriever exposes sources the user should not see.</p>
  </div>
</div>

The last one is easy to underestimate. RAG systems need access control at retrieval time, not only at the user interface. If a user cannot access a document, the retriever should not place that document into the prompt.

## 10. A Practical RAG Checklist

When building a RAG system, I would start with this checklist:

1. **Define the corpus.** What documents are allowed sources?
2. **Preserve metadata.** Can every chunk point back to a document, page, section, or table?
3. **Chunk by meaning.** Do not split blindly if document structure is available.
4. **Use hybrid retrieval.** Combine keyword and semantic search when domain terms matter.
5. **Rerank before generation.** Put the strongest evidence into the limited context window.
6. **Require grounded answers.** Tell the model to cite and to admit missing evidence.
7. **Evaluate with real questions.** Test retrieval recall, citation quality, and answer usefulness.
8. **Monitor drift.** Re-index when documents change and retest when models change.

<div class="llm103-note">
  <p>RAG is not "chat with your PDFs." A serious RAG system is an evidence pipeline: document processing, search, ranking, prompt construction, generation, citation, and evaluation.</p>
</div>
