In LLM 103, we treated Retrieval-Augmented Generation (RAG) as an evidence pipeline. The model receives a question, the system retrieves relevant documents, and the model answers from those sources. That is already more than a plain chatbot.

This post goes one step further: **LLM agents**. An agent is an LLM-powered system that can choose actions, call tools, observe results, keep state, and continue working toward a goal. Agents can be useful, but they are also easy to overbuild. Most problems do not need a fully autonomous loop. They need a small, reliable workflow.

## 1. What Makes Something an Agent?

An ordinary LLM call takes an input and returns an output. An agent has a loop. It can decide what to do next, call a tool, inspect the result, update its plan, and continue.

<div class="llm-flow" role="img" aria-label="LLM agent loop">
  <div class="llm-card">
    <strong>Goal</strong>
    <p>What needs to be done?</p>
  </div>
  <div class="llm-card">
    <strong>Plan</strong>
    <p>Choose a next step.</p>
  </div>
  <div class="llm-card">
    <strong>Act</strong>
    <p>Call a tool or produce work.</p>
  </div>
  <div class="llm-card">
    <strong>Observe</strong>
    <p>Read the result.</p>
  </div>
  <div class="llm-card">
    <strong>Revise</strong>
    <p>Continue, stop, or ask.</p>
  </div>
</div>

The five cards above are not a one-shot sequence. In practice they form a loop: after observing a result, the agent revises its plan and acts again until the goal is met.


<pre class="llm-code"><code>┌─────────────────────────┐
│           GOAL          │
└────────────┬────────────┘
             │
             ▼
       ┌───────────┐
┌────▶│   PLAN     │
│      └─────┬─────┘
│            │
│            ▼
│      ┌───────────┐
│      │    ACT    │─── call tool, write, search
│      └─────┬─────┘
│            │
│            ▼
│      ┌───────────┐
│      │  OBSERVE  │─── read result
│      └─────┬─────┘
│            │
│            ▼
│      ┌───────────┐
└──────┤  REVISE   │─── done? continue? ask human?
       └───────────┘</code></pre>


This loop is powerful because it lets the model interact with the world instead of only describing it. It is risky for the same reason. A bad answer is one thing. A bad action can change files, send messages, spend money, leak data, or corrupt a workflow.

<div class="llm-note">
  <p><strong>Working definition:</strong> an LLM agent is a system where the model helps choose actions over time, usually with tools, memory, and feedback.</p>
</div>

## 2. Tools Are Where Agents Become Useful

Tools let the system move work out of language generation and into reliable operations. A calculator should calculate. A database should query. A search engine should search. A code runner should execute tests. The LLM's job is often to decide **which** tool is needed and **how** to use the result.

<div class="llm-grid">
  <div class="llm-card">
    <strong>Search</strong>
    <p>Find current or external information.</p>
  </div>
  <div class="llm-card">
    <strong>Database</strong>
    <p>Retrieve structured records.</p>
  </div>
  <div class="llm-card">
    <strong>Code</strong>
    <p>Run tests, scripts, or calculations.</p>
  </div>
  <div class="llm-card">
    <strong>Files</strong>
    <p>Read, edit, or transform documents.</p>
  </div>
  <div class="llm-card">
    <strong>Maps</strong>
    <p>Route, geocode, or inspect spatial data.</p>
  </div>
  <div class="llm-card">
    <strong>Messaging</strong>
    <p>Draft, send, or schedule communication.</p>
  </div>
</div>

A useful tool call is structured. The model should not vaguely say "I searched." The system should record the tool name, arguments, result, and whether the result was used in the final answer.

<div class="llm-code">User goal:
Summarize papers on household evacuation decision-making.

Tool call:
search_papers(query="household evacuation decision making risk perception", limit=10)

Observation:
10 candidate papers found.

Next step:
Filter for empirical transportation or disaster behavior studies.</div>

<div class="llm-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2302.04761">Schick et al. (2023), "Toolformer"</a>: explores how language models can learn to decide which APIs to call and how to use the results.</li>
    <li><a href="https://arxiv.org/abs/2205.00445">Karpas et al. (2022), "MRKL Systems"</a>: frames tool-using LLM systems as modular combinations of language, knowledge, and reasoning components.</li>
    <li><a href="https://arxiv.org/abs/2112.09332">Nakano et al. (2021), "WebGPT"</a>: an early browser-assisted question-answering system trained with human feedback and source citation.</li>
  </ul>
</div>

## 3. Planning Is Useful, but Fragile

Many agent demos start with a big goal and ask the model to make a plan. Planning helps when a task has dependencies: gather sources before writing, run tests before reporting, inspect data before modeling.

But LLM plans can be brittle. They can skip necessary steps, invent progress, or keep looping after the useful work is done. Planning works better when the system has clear stopping conditions and observable state.

<div class="llm-two-col">
  <div class="llm-panel">
    <strong>Weak plan</strong>
    <p>Research the topic.</p>
    <p>Write the report.</p>
    <p>Make it good.</p>
  </div>
  <div class="llm-panel">
    <strong>Better plan</strong>
    <p>Find 12 candidate papers.</p>
    <p>Select 6 empirical studies.</p>
    <p>Extract methods and findings.</p>
    <p>Draft a 900-word synthesis with citations.</p>
  </div>
</div>

For complex tasks, the agent should not merely plan. It should check whether each step has actually been completed.

<div class="llm-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2305.10601">Yao et al. (2023), "Tree of Thoughts"</a>: generalizes chain-of-thought prompting into search over alternative intermediate reasoning paths.</li>
    <li><a href="https://arxiv.org/abs/2204.01691">Ahn et al. (2022), "Do As I Can, Not As I Say"</a>: shows why action selection should consider both language intent and what actions are actually feasible.</li>
  </ul>
</div>

## 4. Memory Is Not One Thing

Agent systems often talk about memory, but there are several different kinds.

<div class="llm-grid">
  <div class="llm-card">
    <strong>Context memory</strong>
    <p>Messages and tool results currently inside the prompt.</p>
  </div>
  <div class="llm-card">
    <strong>Working memory</strong>
    <p>Temporary notes, plans, and task state.</p>
  </div>
  <div class="llm-card">
    <strong>Long-term memory</strong>
    <p>Saved facts, preferences, documents, or prior outcomes.</p>
  </div>
</div>

Context memory disappears when it leaves the context window. Working memory is task-specific. Long-term memory persists, which means it needs stronger rules: what is saved, who can see it, when it expires, and how it can be corrected.

Memory can make agents more useful, but sloppy memory can make them worse. If the system saves bad assumptions, private information, or stale preferences, it will retrieve them later with undeserved authority.

<div class="llm-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2304.03442">Park et al. (2023), "Generative Agents"</a>: describes agents with memory streams, reflection, and planning for simulated social behavior.</li>
    <li><a href="https://arxiv.org/abs/2303.11366">Shinn et al. (2023), "Reflexion"</a>: uses verbal feedback and self-reflection as a memory-like mechanism for improving future attempts.</li>
    <li><a href="https://arxiv.org/abs/2305.16291">Wang et al. (2023), "Voyager"</a>: an embodied agent with a skill library and iterative self-improvement in Minecraft.</li>
  </ul>
</div>

## 5. Single-Agent vs Multi-Agent Systems

A single-agent system has one model-driven loop. A multi-agent system creates several roles, such as planner, researcher, coder, reviewer, or critic. These roles can be useful when they create real checks and division of labor.

They can also become theater. If three agents are all the same model with different names and no tools, tests, or external evidence, the system may only produce more confident conversation.

<div class="llm-two-col">
  <div class="llm-panel">
    <strong>Useful multi-agent design</strong>
    <p>Different tools, permissions, or evaluation criteria.</p>
    <p>Clear handoffs and stopping rules.</p>
    <p>Outputs checked against evidence or tests.</p>
  </div>
  <div class="llm-panel">
    <strong>Weak multi-agent design</strong>
    <p>Several personas chatting without new information.</p>
    <p>No execution or verification.</p>
    <p>Longer traces with little extra reliability.</p>
  </div>
</div>

<div class="llm-code">Example: Multi-agent literature review

Agent 1 (Researcher):
  Tools: paper search, PDF reader
  Task: Find 15 papers on evacuation behavior modeling.
  Output: Ranked list with abstracts and relevance scores.

Agent 2 (Analyst):
  Tools: text extraction, table parser
  Task: Extract methods, sample sizes, and key findings from top 8 papers.
  Output: Structured comparison table.

Agent 3 (Reviewer):
  Tools: citation checker, fact verifier
  Task: Verify that the synthesis draft cites only claims present in the source papers.
  Output: Flagged unsupported claims.

Why this works: each agent has different tools, a defined output,
and the reviewer checks the analyst's work against real sources.</div>

Multi-agent systems are most defensible when separation creates a concrete benefit: one agent writes code, another runs tests, another reviews the diff; one retrieves sources, another drafts, another checks citation support.

<div class="llm-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2308.08155">Wu et al. (2023), "AutoGen"</a>: introduces a multi-agent conversation framework for building LLM applications.</li>
    <li><a href="https://arxiv.org/abs/2308.11432">Wang et al. (2023), "A Survey on Large Language Model based Autonomous Agents"</a>: useful for situating single-agent and multi-agent designs in the broader agent literature.</li>
  </ul>
</div>

## 6. Guardrails: The Boring Part That Matters

An agent with tools needs boundaries. Guardrails are not just content filters. They are system constraints that make bad actions harder.

Useful guardrails include:

- tool permissions;
- read-only modes;
- approval gates for risky actions;
- input validation;
- output schemas;
- rate limits and budgets;
- audit logs;
- rollback plans;
- restricted memory access;
- human review for high-impact decisions.

<div class="llm-panel">
  <strong>Risk budget example</strong>
  <div class="llm-status"><span>Read files</span><div class="llm-bar"><span style="width: 85%;"></span></div></div>
  <div class="llm-status"><span>Edit draft</span><div class="llm-bar"><span style="width: 60%;"></span></div></div>
  <div class="llm-status"><span>Run tests</span><div class="llm-bar"><span style="width: 55%;"></span></div></div>
  <div class="llm-status"><span>Publish</span><div class="llm-bar"><span style="width: 15%;"></span></div></div>
  <p class="llm-small">Higher bars mean lower risk or less required approval. Publishing should usually require explicit human control.</p>
</div>

The best agent systems make safe actions easy and risky actions explicit. If a tool can send an email, move money, delete files, or change public content, the agent should not casually call it in an unreviewed loop.

## 7. Evaluation for Agents

Evaluating an agent is harder than evaluating a single answer. You need to inspect the path, not only the final output.

Ask:

- Did the agent choose appropriate tools?
- Did it use tool results correctly?
- Did it stop when the task was done?
- Did it ask for help when blocked?
- Did it avoid actions outside its permission scope?
- Could a human audit what happened?
- Did the workflow improve over a simpler non-agent baseline?

<div class="llm-note">
  <p><strong>The baseline question:</strong> would this task be better handled by one prompt, a deterministic script, or a RAG answer? If yes, do that first.</p>
</div>

Agent evaluation should include success rate, cost, latency, number of tool calls, failure recovery, and human review burden. A system that succeeds 5 percent more often but costs 10 times as much and creates unreadable traces may not be an improvement.

## 8. When Not to Build an Agent

Not every LLM workflow needs agency. Many useful systems are deliberately boring:

- a summarizer with a carefully designed prompt;
- a RAG assistant with citations;
- a script that extracts fields from documents;
- a classifier with human review;
- a dashboard that uses an LLM only to explain selected results.

Build an agent when the task truly requires multiple steps, tool use, state tracking, and adaptive decisions. Avoid an agent when the task is stable, repeatable, and better expressed as a deterministic pipeline.

<div class="llm-grid">
  <div class="llm-card">
    <strong>Use a prompt</strong>
    <p>The task is short and self-contained.</p>
  </div>
  <div class="llm-card">
    <strong>Use RAG</strong>
    <p>The task needs external evidence.</p>
  </div>
  <div class="llm-card">
    <strong>Use an agent</strong>
    <p>The task needs actions, feedback, and adaptation.</p>
  </div>
</div>

## 9. A Practical Agent Checklist

Before building an agent, I would write down:

1. **Goal:** What outcome counts as done?
2. **Tools:** What actions can the system take?
3. **Permissions:** Which actions require approval?
4. **State:** What must be remembered during the task?
5. **Memory:** What, if anything, persists afterward?
6. **Stopping rule:** When should the loop end?
7. **Fallback:** When should it ask a human?
8. **Evaluation:** How will success, cost, and risk be measured?
9. **Audit:** Can someone reconstruct what happened?

<div class="llm-note">
  <p>Agents are not magic autonomy dust. They are workflows where an LLM helps choose actions. The engineering challenge is to make those actions observable, reversible when possible, and worth the added complexity.</p>
</div>
