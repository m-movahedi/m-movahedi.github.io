In LLM 106, we looked at fine-tuning and adaptation. That gave us a way to change model behavior when prompting, retrieval, and tools are not enough. Now we move from model behavior to system behavior.

An LLM prototype can be a notebook, a prompt, and a few examples. A deployed LLM system is different. It has users, latency expectations, costs, logs, privacy constraints, model updates, failures, and maintenance work. This post focuses on the practical side: model choice, inference cost, serving, caching, monitoring, privacy, and operational reliability.

## 1. Deployment Is a System Problem

The model is only one component. A deployed LLM application usually includes prompts, retrieval, tools, routing, user interface, logging, monitoring, safety checks, access control, and evaluation.

<div class="llm107-flow" role="img" aria-label="LLM deployment stack">
  <div class="llm107-card">
    <strong>User</strong>
    <p>Task, context, and expectations.</p>
  </div>
  <div class="llm107-card">
    <strong>Orchestrator</strong>
    <p>Prompting, routing, and policies.</p>
  </div>
  <div class="llm107-card">
    <strong>Knowledge</strong>
    <p>RAG, files, databases, and tools.</p>
  </div>
  <div class="llm107-card">
    <strong>Model</strong>
    <p>Inference, generation, and scoring.</p>
  </div>
  <div class="llm107-card">
    <strong>Monitoring</strong>
    <p>Quality, cost, latency, and risk.</p>
  </div>
</div>

The core deployment question is not "Can the model answer this once?" It is "Can the system answer this reliably, affordably, and safely for real users?"

<div class="llm107-note">
  <p><strong>Practical framing:</strong> deployment turns model quality into service quality. Service quality includes latency, cost, privacy, observability, uptime, and user trust.</p>
</div>

## 2. Choosing a Model

Model choice is a tradeoff. Larger models often perform better on difficult reasoning and broad knowledge tasks, but they cost more and are slower. Smaller models can be cheaper, faster, easier to host, and good enough for narrow workflows.

<div class="llm107-grid">
  <div class="llm107-card">
    <strong>Large model</strong>
    <p>Better for complex reasoning, broad tasks, and messy language.</p>
  </div>
  <div class="llm107-card">
    <strong>Small model</strong>
    <p>Better for speed, cost, classification, extraction, and constrained tasks.</p>
  </div>
  <div class="llm107-card">
    <strong>Model router</strong>
    <p>Send easy tasks to cheaper models and hard tasks to stronger models.</p>
  </div>
</div>

For many applications, the best system uses more than one model. A small model might classify intent, a retrieval system might gather evidence, and a stronger model might synthesize the final answer.

Important model-choice questions:

- What task must the model perform?
- Does it need tool use or structured output?
- How much context does it need?
- What is the acceptable latency?
- What is the cost per successful task, not just cost per token?
- Can data leave your environment?
- How will you evaluate regressions after model changes?

## 3. Latency: Time to First Token and Time to Done

LLM latency has two parts. **Time to first token** is how long the user waits before seeing the answer begin. **Time to completion** is how long the full answer takes.

Long prompts increase prefill time. Long answers increase decoding time. Tool calls, retrieval, reranking, and safety checks add their own latency.

<div class="llm107-panel">
  <strong>Latency budget example</strong>
  <div class="llm107-row"><span>Retrieval</span><div class="llm107-bar"><span style="width: 18%;"></span></div><span>low</span></div>
  <div class="llm107-row"><span>Reranking</span><div class="llm107-bar"><span style="width: 28%;"></span></div><span>med</span></div>
  <div class="llm107-row"><span>Prefill</span><div class="llm107-bar"><span style="width: 42%;"></span></div><span>med</span></div>
  <div class="llm107-row"><span>Decoding</span><div class="llm107-bar"><span style="width: 76%;"></span></div><span>high</span></div>
  <p class="llm107-small">Illustrative only. The shape changes with model size, context length, hardware, batching, and output length.</p>
</div>

Useful latency techniques include:

- streaming tokens to the user;
- reducing prompt size;
- retrieving fewer but better chunks;
- caching repeated prompts or retrieval results;
- using smaller models for simple tasks;
- batching requests when throughput matters;
- limiting output length;
- using faster decoding or serving systems.

<div class="llm107-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2205.14135">Dao et al. (2022), "FlashAttention"</a>: important for memory-efficient and IO-aware attention computation.</li>
    <li><a href="https://arxiv.org/abs/2302.01318">Chen et al. (2023), "Accelerating Large Language Model Decoding with Speculative Sampling"</a>: explains draft-and-verify decoding as a way to reduce generation latency.</li>
  </ul>
</div>

## 4. Cost Is More Than Tokens

Token cost matters, but it is not the whole bill. A deployed system may pay for model calls, embedding calls, vector databases, rerankers, tool execution, storage, monitoring, human review, and engineering maintenance.

Think in terms of **cost per successful task**:

<div class="llm107-code">Cost per successful task =
  model calls
+ retrieval and reranking
+ tool calls
+ retries
+ human review
+ infrastructure
divided by successful completed workflows</div>

A cheap model that fails often can be more expensive than a stronger model that succeeds with fewer retries. A long prompt that avoids one tool call may still cost more than a short prompt with a deterministic tool.

<div class="llm107-note">
  <p><strong>Deployment habit:</strong> measure cost, latency, and quality together. Optimizing only one usually makes the other two worse.</p>
</div>

## 5. Serving and the KV Cache

During generation, transformer models store key-value representations for previous tokens. This **KV cache** avoids recomputing the entire history at every step. It is essential for efficient decoding, but it can use a lot of memory.

Serving systems care about:

- how many requests can run at once;
- how long each request is;
- how much KV cache memory is needed;
- whether requests can be batched;
- whether shared prefixes can reuse computation;
- how to schedule work under load.

<div class="llm107-two-col">
  <div class="llm107-panel">
    <strong>Without efficient cache management</strong>
    <p>GPU memory fragments.</p>
    <p>Long requests block shorter ones.</p>
    <p>Throughput suffers under load.</p>
  </div>
  <div class="llm107-panel">
    <strong>With efficient cache management</strong>
    <p>Memory is reused more carefully.</p>
    <p>Batching becomes more practical.</p>
    <p>Serving cost can improve.</p>
  </div>
</div>

<div class="llm107-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2309.06180">Kwon et al. (2023), "Efficient Memory Management for Large Language Model Serving with PagedAttention"</a>: introduces PagedAttention and vLLM for high-throughput LLM serving.</li>
    <li><a href="https://arxiv.org/abs/1911.02150">Shazeer (2019), "Fast Transformer Decoding: One Write-Head is All You Need"</a>: an important reference for multi-query attention and faster decoding.</li>
  </ul>
</div>

## 6. Quantization and Compression

Quantization reduces the precision used to store or compute with model weights. The goal is to reduce memory and sometimes increase speed while keeping quality acceptable.

This is especially important when deploying models on limited hardware. But quantization is a tradeoff. Lower precision can reduce quality, affect rare tasks, or interact badly with certain model architectures.

<div class="llm107-grid">
  <div class="llm107-card">
    <strong>FP16/BF16</strong>
    <p>Common high-quality inference precision.</p>
  </div>
  <div class="llm107-card">
    <strong>INT8</strong>
    <p>Often useful for memory reduction with manageable quality impact.</p>
  </div>
  <div class="llm107-card">
    <strong>4-bit</strong>
    <p>Very memory efficient, but needs careful evaluation.</p>
  </div>
</div>

Always evaluate the quantized model on your actual task. A quantized model may look fine on casual chat but fail on structured extraction, citations, math, or domain-specific wording.

<div class="llm107-papers">
  <strong>Important papers for this section</strong>
  <ul>
    <li><a href="https://arxiv.org/abs/2208.07339">Dettmers et al. (2022), "LLM.int8()"</a>: studies 8-bit matrix multiplication for large transformer inference.</li>
    <li><a href="https://arxiv.org/abs/2210.17323">Frantar et al. (2022), "GPTQ"</a>: a widely cited post-training quantization method for generative transformer models.</li>
    <li><a href="https://arxiv.org/abs/2211.10438">Xiao et al. (2022), "SmoothQuant"</a>: an important post-training quantization approach for large language models.</li>
  </ul>
</div>

## 7. Caching

Caching can reduce cost and latency, but only when used carefully.

Useful cache targets include:

- embeddings for documents;
- retrieval results for repeated queries;
- reranking results;
- prompt prefixes;
- tool outputs;
- final answers for deterministic or low-risk tasks.

Caching is less safe when answers depend on user permissions, current data, or private context. If two users ask the same question but have different document access, they should not automatically receive the same cached answer.

<div class="llm107-note">
  <p><strong>Cache rule:</strong> cache stable computations, not sensitive decisions. Include permissions, source versions, and prompt versions in cache keys when they affect the answer.</p>
</div>

## 8. Monitoring Quality in Production

You cannot manually inspect every output. You need monitoring signals.

Track:

- latency;
- cost;
- token counts;
- retry rate;
- tool-call failure rate;
- retrieval hit rate;
- citation coverage;
- user corrections;
- escalation rate;
- refusal rate;
- human review findings.

<div class="llm107-grid">
  <div class="llm107-card">
    <strong>System metrics</strong>
    <p>Latency, errors, uptime, throughput.</p>
  </div>
  <div class="llm107-card">
    <strong>Model metrics</strong>
    <p>Answer quality, grounding, refusals, drift.</p>
  </div>
  <div class="llm107-card">
    <strong>User metrics</strong>
    <p>Task success, corrections, trust, adoption.</p>
  </div>
</div>

Monitoring should connect back to evaluation. If your evaluation says citation quality matters, production monitoring should track citation failures. If your agent has tools, monitor tool calls and not only final text.

## 9. Privacy, Logging, and Data Boundaries

LLM systems often touch sensitive data: documents, prompts, user messages, tool outputs, identifiers, and metadata. Deployment requires explicit data boundaries.

Questions to answer before launch:

- What data is sent to the model provider?
- What is logged?
- How long are logs retained?
- Can logs contain private documents or personal information?
- Who can inspect traces?
- Are retrieved documents filtered by user permissions?
- Can users request deletion or correction?
- Are prompts and outputs used for future training?

<div class="llm107-two-col">
  <div class="llm107-panel">
    <strong>Unsafe habit</strong>
    <p>Log every prompt and retrieved document by default.</p>
  </div>
  <div class="llm107-panel">
    <strong>Safer habit</strong>
    <p>Log only what is needed, redact sensitive data, and separate debugging from production retention.</p>
  </div>
</div>

Privacy is not a layer you add at the end. It affects model choice, hosting choice, retrieval permissions, logging, monitoring, and review workflows.

## 10. Rollouts and Regression Testing

LLM systems should be rolled out like software systems, not like one-off demos.

Use:

- staging environments;
- fixed evaluation sets;
- canary releases;
- prompt and model versioning;
- rollback plans;
- human review for high-risk outputs;
- monitoring dashboards;
- incident notes when failures occur.

<div class="llm107-code">Deployment checklist

Model version: recorded
Prompt version: recorded
RAG index version: recorded
Tool permissions: reviewed
Evaluation set: passed
Latency budget: passed
Cost budget: passed
Rollback plan: ready
Monitoring: enabled</div>

The boring versioning details matter. If quality gets worse, you need to know whether the model changed, the prompt changed, the retriever changed, the documents changed, or user behavior changed.

## 11. A Practical Deployment Checklist

Before shipping an LLM feature, I would check:

1. **Task definition:** What workflow does this support?
2. **Model choice:** Why this model, and what is the fallback?
3. **Prompt versioning:** Can you reproduce a prior output?
4. **Context design:** What enters the prompt, and why?
5. **Cost controls:** Are there token, retry, and tool-call budgets?
6. **Latency controls:** Is streaming, caching, or routing needed?
7. **Privacy rules:** What data is sent, stored, redacted, or blocked?
8. **Evaluation:** What local tests must pass before release?
9. **Monitoring:** What signals show quality, risk, and cost?
10. **Rollback:** How do you revert a bad model, prompt, or index update?

<div class="llm107-note">
  <p>Deployment is where LLM work becomes engineering. A good system is not just impressive on a prompt. It is observable, bounded, affordable, testable, and useful under real conditions.</p>
</div>
